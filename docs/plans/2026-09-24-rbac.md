# RBAC: Roles, Permissions & Access Panel — Implementation Plan

## Goal

Extend auth from 2 roles to 4 (EMPLOYEE, MANAGER, ADMIN, SUPER_ADMIN), add a per-module permission system (role defaults + per-user overrides), and an Access Panel UI with a checkbox grid (modules × View/Edit/Delete + special actions).

## Decisions (confirmed with user)

- Roles: keep MANAGER; add ADMIN and SUPER_ADMIN. Rank: EMPLOYEE(0) < MANAGER(1) < ADMIN(2) < SUPER_ADMIN(3).
- "Staff" = MANAGER | ADMIN | SUPER_ADMIN. All staff use the existing `/manager/*` portal ("admins play role as managers").
- Permissions = role defaults + per-user overrides (stored in DB, grant or revoke).
- Panel grid: rows = modules, columns = View / Edit / Delete + module-specific actions.
- Work directly on `main` (user consent given). Existing uncommitted changes in 5 files must be left intact — do not revert or stage them unless they are part of your task.

## Permission catalogue (`lib/permissions.ts`)

Permission keys are `"<module>.<action>"`.

| Module | Actions |
|---|---|
| `timesheets` | view, edit, delete, approve, reopen |
| `mis` | view, edit (generate/preview), delete, finalize |
| `clients` (Clients, Projects & Tasks) | view, edit, delete |
| `sandbox` | view, edit, delete |
| `employees` | view, edit, delete |
| `access` (the Access Panel itself) | view, edit |

Role defaults:
- EMPLOYEE: none (employees' own-timesheet rights are ownership-based and not governed by this system).
- MANAGER: every permission except `access.*`.
- ADMIN: every permission.
- SUPER_ADMIN: every permission, **not overridable** (overrides ignored).

Rules:
- Overrides only apply to MANAGER and ADMIN users. EMPLOYEE cannot receive module permissions (middleware blocks them from `/manager` anyway). SUPER_ADMIN always has all.
- Role management: an actor may create/edit/deactivate/assign a role only for users (and target roles) of strictly lower rank — except SUPER_ADMIN, who may manage any role including ADMIN and SUPER_ADMIN. So: SUPER_ADMIN adds admins; ADMIN manages MANAGER/EMPLOYEE; MANAGER manages EMPLOYEE only.
- Nobody may deactivate themselves or change their own role.
- The last active SUPER_ADMIN cannot be demoted or deactivated.
- Access Panel edit: actor needs `access.edit`, target rank must be strictly lower than actor rank (SUPER_ADMIN may edit anyone below SUPER_ADMIN), and actor may not grant a permission they don't hold themselves.
- Re-open: moves an APPROVED timesheet back to DRAFT, clearing `approvedAt`, so the owner can edit and resubmit. Needs `timesheets.reopen`.

## Data model

```prisma
enum Role { EMPLOYEE MANAGER ADMIN SUPER_ADMIN }

model UserPermission {
  id        Int      @id @default(autoincrement())
  userId    Int
  user      User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  module    String
  action    String
  granted   Boolean  // true = grant beyond role default, false = revoke role default
  updatedAt DateTime @updatedAt
  @@unique([userId, module, action])
  @@index([userId])
}
// User gets: permissions UserPermission[]
```

Permissions are resolved **from the DB on every request** (not stored in the JWT) so panel changes take effect immediately. The JWT keeps `role` only, for middleware's coarse gate.

## Task 2 — Pure permission logic + tests

Files: `lib/permissions.ts`, `lib/permissions.test.ts`, `package.json` (add `"test": "node --import tsx --test lib/**/*.test.ts"` — or an equivalent glob that works on Windows Git Bash and PowerShell; `tsx` is already a devDependency; no new deps).

`lib/permissions.ts` must be pure (no prisma / next imports) so it can be imported by client components and middleware. Export:
- `ROLES`, `Role`, `ROLE_RANK`, `STAFF_ROLES`, `isStaffRole(role)`.
- `MODULES`: ordered array of `{ key, label, actions: Action[] }` matching the catalogue table (labels: "Timesheets", "MIS Reports", "Clients & Projects", "Sandbox MIS", "Employees", "Access Panel"). Action labels: View, Edit, Delete, Approve, Re-open, Finalize.
- `type Permission = \`${module}.${action}\`` (a string union derived from MODULES is ideal, a plain string alias is acceptable), `ALL_PERMISSIONS`.
- `roleDefaults(role): Set<Permission>`.
- `resolvePermissions(role, overrides: {module, action, granted}[]): Set<Permission>` — applies the rules above (SUPER_ADMIN ignores overrides; EMPLOYEE ignores overrides; unknown module/action keys ignored).
- `diffOverrides(role, desired: Permission[]): {module, action, granted}[]` — minimal override rows to turn role defaults into `desired`.
- `canManageRole(actorRole, targetRole): boolean`.
- `canEditAccess(actorRole, actorPerms, targetRole): boolean`.
- Tests (node:test + node:assert) covering: each role's defaults, grant override, revoke override, SUPER_ADMIN ignores overrides, EMPLOYEE ignores overrides, diffOverrides round-trips through resolvePermissions, canManageRole matrix, canEditAccess.
- Verify: `npm test` passes, `npx tsc --noEmit` passes.
